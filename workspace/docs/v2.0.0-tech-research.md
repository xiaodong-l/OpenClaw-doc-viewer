## 1️⃣ SAML 2.0 / OIDC 集成 POC

### 研究目标
验证 SSO 集成的技术可行性和工作量估算

### 技术方案对比

| 方案 | 类型 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **Keycloak** | 开源 IdP | 免费、功能全、可自托管 | 需要运维、资源占用 | ⭐⭐⭐⭐⭐ |
| **Auth0** | SaaS | 开箱即用、免运维 | 费用高 ($23/月/MAU) | ⭐⭐⭐⭐ |
| **Okta** | SaaS | 企业级、支持好 | 费用高 ($2/用户/月) | ⭐⭐⭐⭐ |
| **Azure AD** | SaaS | 微软生态集成 | 配置复杂 | ⭐⭐⭐ |
| **自研** | 自研 | 完全可控 | 工作量大、风险高 | ⭐⭐ |

### 推荐方案：Keycloak

**理由:**
- 开源免费，降低运营成本
- 支持 SAML 2.0、OIDC、OAuth2
- 可自托管，数据可控
- 社区活跃，文档完善

## 2️⃣ 文档版本控制 POC

### 研究目标
验证文档版本历史和回滚的技术实现方案

### 技术方案对比

| 方案 | 存储方式 | 优点 | 缺点 | 推荐度 |
|------|----------|------|------|--------|
| **Git 后端** | Git 仓库 | 版本清晰、diff 方便 | 学习曲线、性能 | ⭐⭐⭐⭐ |
| **数据库版本表** | 关系数据库 | 查询快、易集成 | 存储开销大 | ⭐⭐⭐⭐ |
| **文档快照** | 对象存储 | 简单、成本低 | diff 复杂 | ⭐⭐⭐ |
| **CRDT** | 特殊数据结构 | 实时协作 | 实现复杂 | ⭐⭐ |

### 推荐方案：数据库版本表

**理由:**
- 与现有架构一致 (PostgreSQL)
- 查询性能好
- 实现复杂度适中
- 易于扩展

### 数据模型设计

```sql
-- 文档主表
CREATE TABLE documents (
  id UUID PRIMARY KEY,
  path VARCHAR(2048) UNIQUE NOT NULL,
  title VARCHAR(512),
  current_version_id UUID,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  created_by UUID REFERENCES users(id),
  updated_by UUID REFERENCES users(id)
);

-- 文档版本表
CREATE TABLE document_versions (
  id UUID PRIMARY KEY,
  document_id UUID REFERENCES documents(id),
  version_number INTEGER NOT NULL,
  content TEXT NOT NULL,
  content_hash VARCHAR(64),
  change_summary VARCHAR(1024),
  created_at TIMESTAMP DEFAULT NOW(),
  created_by UUID REFERENCES users(id),
  
  UNIQUE(document_id, version_number)
);

-- 版本对比缓存
CREATE TABLE version_diffs (
  id UUID PRIMARY KEY,
  from_version_id UUID REFERENCES document_versions(id),
  to_version_id UUID REFERENCES document_versions(id),
  diff_json JSONB,
  created_at TIMESTAMP DEFAULT NOW()
);

-- 索引
CREATE INDEX idx_document_versions_doc_id ON document_versions(document_id);
CREATE INDEX idx_document_versions_created ON document_versions(created_at DESC);
```

### API 设计

```javascript
// 获取文档版本列表
GET /api/v2/documents/:id/versions
Response: {
  versions: [
    {
      id: "uuid",
      versionNumber: 3,
      createdAt: "2026-03-13T10:00:00Z",
      createdBy: { id: "uuid", name: "张三" },
      changeSummary: "更新权限配置章节"
    }
  ]
}

// 获取特定版本内容
GET /api/v2/documents/:id/versions/:versionId
Response: {
  id: "uuid",
  content: "...",
  versionNumber: 3,
  ...
}

// 版本对比
GET /api/v2/documents/:id/versions/:fromId/diff/:toId
Response: {
  added: ["..."],
  removed: ["..."],
  modified: ["..."]
}

// 回滚到指定版本
POST /api/v2/documents/:id/versions/:versionId/rollback
Request: {
  reason: "回滚原因"
}
Response: {
  success: true,
  newVersionId: "uuid"
}
```

### 版本创建策略

```javascript
// 自动版本控制
- 每次保存自动创建新版本
- 同一用户 5 分钟内修改合并为一个版本
- 每天最多 10 个版本 (避免爆炸)

// 手动版本控制
- 用户可手动创建版本标记
- 可添加版本说明
- 可标记为重要版本 (长期保留)

// 版本清理
- 保留最近 30 天的所有版本
- 30 天前保留每天第一个版本
- 重要版本永久保留
```

## 4️⃣ 多租户数据隔离 (研究 - 延期到 v3.0)

### 研究目标
评估多租户架构的实现方案

### 方案对比

| 方案 | 隔离级别 | 成本 | 复杂度 | 推荐场景 |
|------|----------|------|--------|----------|
| **数据库隔离** | 高 | 高 | 中 | 大型企业 |
| **Schema 隔离** | 中 | 中 | 高 | 中型企业 |
| **行级隔离** | 低 | 低 | 低 | 小型企业 |

### 推荐方案：行级隔离 (v2.0) → Schema 隔离 (v3.0)

**v2.0 行级隔离:**
```sql
-- 所有租户共享表，通过 tenant_id 区分
CREATE TABLE documents (
  id UUID,
  tenant_id UUID,
  ...
);

-- 所有查询必须带 tenant_id
SELECT * FROM documents WHERE tenant_id = ?;
```

**v3.0 Schema 隔离:**
```sql
-- 每个租户独立 Schema
CREATE SCHEMA tenant_abc123;
CREATE TABLE tenant_abc123.documents (...);

-- 查询时切换 Schema
SET search_path TO tenant_abc123;
SELECT * FROM documents;
```

### 结论
⏸️ **延期到 v3.0**，v2.0 使用行级隔离满足需求
